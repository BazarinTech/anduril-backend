Two findings that changed the plan

Critical The session cookie's name is the JWT signing secret

The frontend mints tokens in a Next.js route handler and sets the cookie as name: "susyr7q3ycugfWDFF". That string is the exact value of JWT_SECRET on the PHP side. The HS256 signing key is therefore published to every visitor as a cookie name — visible in DevTools, no exploitation needed. Anyone can forge a token for any userID.

Good news buried in it: the secret is not in the browser bundle, and the BFF split is otherwise sound. Fixing it is a rename plus a rotation across both repos. Promoted to the front of Phase 2 as item 2.0.

Trap Your two vendor trees are different code under the same version

admin/vendor/ and backend/vendor/ both ship bazarin/bazarin-php-library tagged v1.1.0, but the backend copy was hand-edited in place and the version was never bumped.

The concurrency tests found a bug the code review had not. Locking the wallet keeps the arithmetic correct but does not stop a deposit being applied twice: the status = 'Pending' check ran before the transaction opened, so eight simultaneous callback deliveries all passed it and all credited. Idempotency needs the status change to be the claim — a conditional UPDATE only one caller can win. That is now claim_transaction(), shared by both callbacks and the admin approval.

Folded in along the way: findings 4.3 and 4.4 are closed. The two divergent commission functions (three levels in the callback, two in the admin approval) are replaced by one walk that climbs the upline chain, stops when it runs out, and cannot dereference a missing row — which was the source of the userID cannot be null fatal. Finding 4.7 (investing in an inactive product) and 4.9 (undefined bonus response) are closed too, since both sat inside the transactions being rewritten.

Claiming runs on the clock, not on a reset

Complete

Whether an investment could be claimed was stored state: orders.rolls, a flag something external had to set back to 1 every night. First an admin pressing a button, later a cron job — both share the same failure mode. Miss a night and nobody can claim; run it twice and everybody claims twice. The product quietly stopped working whenever the thing that maintained the flag did not run.

Claimability is now derived: an order can be claimed while the clock is inside the configured daily window and that order has claims left for the current period. Nothing has to fire on a schedule for tomorrow to work, and there is no state to go stale.
