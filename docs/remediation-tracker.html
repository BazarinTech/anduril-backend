Three things I can't do from here

  1. Rotate every credential at its provider. Moving secrets out of the source tree does not un-leak them — they are in git history. Rotate: the MySQL password, the Palpluss pp_live_ key, the SMTP mailbox password, the HostPinnacle API key, and the dead PayHero / SwiftWallet / Umeskia keys still sitting in commented-out blocks. JWT_SECRET and the callback token are already rotated and have never been in git.
  2. Run the credential migration on any database that predates Phase 2. php db/migrations/001_phase2_hashed_credentials.php. Logins compare against a hash now, so an unmigrated database locks everyone out — including you. It is safe to re-run.
  3. Create config/env.php on the server. It is gitignored by design, so a deploy will not carry it. Copy config/env.example.php and fill it in, or set real environment variables — those take precedence over the file.
  4. Decide the vendor/ strategy. The two vendored copies of your library have drifted apart (see below). Until that is resolved they must stay in git, and composer install is unsafe to run.
  5. Pin CORS_ORIGIN when the frontend domain is settled. Held open by decision — the allowlist logic is already live, so this is a one-line config edit with no code change. Until then any origin may call the API.
Surfaced during Phase 0

Two findings that changed the plan

Critical The session cookie's name is the JWT signing secret

The frontend mints tokens in a Next.js route handler and sets the cookie as name: "susyr7q3ycugfWDFF". That string is the exact value of JWT_SECRET on the PHP side. The HS256 signing key is therefore published to every visitor as a cookie name — visible in DevTools, no exploitation needed. Anyone can forge a token for any userID.

Good news buried in it: the secret is not in the browser bundle, and the BFF split is otherwise sound. Fixing it is a rename plus a rotation across both repos. Promoted to the front of Phase 2 as item 2.0.

Trap Your two vendor trees are different code under the same version

admin/vendor/ and backend/vendor/ both ship bazarin/bazarin-php-library tagged v1.1.0, but the backend copy was hand-edited in place and the version was never bumped.

The clocks did not agree

Fixed

Found while testing 2.4, and much larger than the item that exposed it. PHP ran in UTC while MySQL ran in EAT, so strtotime() on any column read back from the database landed three hours in the future and every age calculation came out negative. Nothing time-based had ever expired.

tz PHP and the MySQL session pinned to one configured zone — which also restored coupon expiry, the deposit throttle, and “users joined today”, none of which had ever worked Done bootstrap/bootstrap.php · config → APP_TIMEZONE
